**现场唯一的可用管理通道是无线的 `hdc` → `192.168.10.180:8710`（直连 `hdcd`；回退才用 `hdcrelay` 的 10178）。USB 通道当前可用（见上方更新）。**

绝对禁止（任一操作都可能直接切断无线，且无法远程恢复）：

1. **重启 CPRO 现在可恢复，但仍不该在关键试验中随手重启**。20:41 的实测表明：重启后无线 8710 自启、USB 由 `hdcd` 自动重建，本机只需 `tconn`。旧结论“重启即永久失联”已作废。
2. **不要执行 `hdc tmode`**（任何形式）。它会重启 `hdcd`，把 persist 模式改成 usb，从而关闭 8710 的 TCP 监听。
3. **不要 `stop hdcd` / `kill hdcd` / 修改 `persist.hdc.mode*`**。同理会中断 8710。
4. **不要 kill 设备上的 `hdcrelay` 进程**（当前 PID 17749，父进程 58027），那是无线的唯一转发。
5. **不要改 CPRO 的 `eth0` / `ip rule` / 路由**。那会连带影响机器人 DDS 链路。
6. **不要在本机执行 `hdc kill`**（虽然可恢复，但会先丢失 tconn，增加一次不必要的风险窗口）。

允许且已安全验证过的操作：只读查询（`cat` / `ls` / `readlink` / `dmesg` / `ps` / `netstat`），以及 gadget configfs 的 `f1` 补链 + `UDC` 重绑（已多次执行，无线始终保持 `Connected`）。

## 5. 目前无法解释的核心矛盾（请重点看这里）

- 端口层与 gadget 层说法冲突：`extcon1 = USB=1`（收到 VBUS）但 `UDC state = not attached`；而 `extcon1` 已被证明是死值，所以真实情况更可能是**根本没有 VBUS**。
- 若是“没有 VBUS”，则说明这条 A-C 链路此刻**连供电都没建立**；但这根线 + 这两个口在 3 小时前还正常枚举过。
- 因此嫌疑集中在两处，尚未分辨：
  - **A. 本机 USB-C 口的供电/端口状态卡住**（热插拔后常见，需换口或重启本机）；
  - **B. CPRO 的 USB-A 母座在反复插拔后接触不良/损坏**。

## 7. 已知可用的修复手法（仅针对 gadget 配置层）

`f1` 消失时（典型症状：`dmesg` 出现 `udc ea100000.hiusbc: failed to start g1: -22`、`UDC` 写不进去）按顺序执行，root shell：

```sh
ln -s /config/usb_gadget/g1/functions/ffs.hdc /config/usb_gadget/g1/configs/b.1/f1
echo ea100000.hiusbc > /config/usb_gadget/g1/UDC
```

成功判据：`cat /config/usb_gadget/g1/UDC` 返回 `ea100000.hiusbc`，`dmesg` 出现 `hiusbc_gadget_pullup: is_on = 1`，随后 Windows 出现 `HDC Device`，`hdc -t 0123456789ABCDEF shell id` 返回 root。

**重要**：该修复不持久，而且实测**每次 USB 断开后 `f1` 都可能再次消失**（10:27 修好 → 11:40 又缺失），怀疑是这台 CPRO 的 `hdcd` 在断连时重建 gadget 不完整。这是本次现象里最值得深挖的软件线索。

## 8. 诊断方不要做的事

- 不要执行 `hdc tmode`：会重启 `hdcd`（约 5 分钟）并可能切断当前唯一可用通道（无线 `10178`）。
- 不要向 `/config/usb_gadget/g1/UDC` 写空值做试探（会解绑 gadget，且配置不完整时会卡在 `-EINVAL`）。
- 不要改 CPRO 的 `eth0` / `ip rule` / `hdcrelay`：那是机器人 DDS 链路与当前唯一管理通道。
- 不要重启 CPRO：`hdcrelay` 不随重启存活，重启会同时失去无线 HDC，只剩 USB（而 USB 正是当前故障点）。
