## 3. 已实现的最小安全壳

安全壳只在 `PolicyHandoff / PolicyWalk / Brake` 期间生效，不改变已通过的 FixStand/FixSquat。

### 3.1 命令整形

- `vx/vy/wz` 加速度上限：`0.20 / 0.10 / 0.20` 单位每秒平方。
- 减速度上限：`0.40 / 0.20 / 0.40` 单位每秒平方。
- 当前 R214 motion 限幅为 `0.10 / 0.05 / 0.10`，因此满量程约 0.5 s 进入、0.25 s 回零。
- 日志同时输出 `requested` 与 `applied`，不能只看摇杆原始值。

### 3.2 遥控输入超时

- `wireless_remote` 头必须为 `0x55,0x51`，轴值必须 finite 且绝对值不超过 1.5。
- 连续 200 ms 收不到合法遥控负载，触发受控 `Brake`，不是继续保持旧速度。
- 限制：HG 内嵌 40 字节没有可见 sequence/timestamp。如果固件持续重复一帧“格式合法但陈旧”的 payload，发布端无法区分它与用户保持摇杆不动。不要把当前实现宣传为完整链路失联检测。

### 3.3 运行中 warning/hard 守卫

| 指标 | Warning | Hard |
|---|---:|---:|
| 腿 `|dq|` | 5 rad/s | 8 rad/s |
| 轮 `|dq|` | 8 rad/s | 12 rad/s |
| 腿 `|tau_est|` | 35 Nm | 50 Nm |
| 轮 `|tau_est|` | 8 Nm | 12 Nm |
| 腿预计 PD 力矩 | 35 Nm | 50 Nm |
| 轮预计 PD 力矩 | 8 Nm | 15 Nm |
| 腿单帧目标跳变 | 0.20 rad/20 ms | 0.35 rad/20 ms |
| 轮单帧目标跳变 | 15 rad/s/20 ms | 30 rad/s/20 ms |

- Warning 连续 5 个 50 Hz 策略帧：受控 `Brake`。
- Hard 连续 3 帧：`EmergencyDamping`。这可能导致站立时失去主动支撑，因此它不是“无风险急停”。
- 任一有效轴 `motorstate != 0` 按 hard 条件处理。
- 预计 PD 力矩为 `kp*(q_cmd-q)+kd*(dq_cmd-dq)`；`LowCmd.tau=0` 只表示无前馈力矩，不代表没有电机力矩。
- `tau_est` 的固件语义未被厂商完整公开，故采用连续帧和 warning/hard 两级，不能凭单点调阈值。

### 3.4 阈值来源与适用边界

R214 训练 trace 的离线统计：预计腿 PD 力矩 p95/p99/max 约 `18.85/22.31/37.87 Nm`；腿 dq `2.23/4.07/7.87 rad/s`；腿目标跳变 `0.0546/0.1098/0.2839 rad`。R284 真机事故达到腿 dq `11.49`、轮 dq `14.38 rad/s`、腿 tau_est `73.4 Nm`。

因此当前数值是“低速早期 bring-up 档”，目标是比事故更早退出，不是 AS2-W 官方能力值，也不是 R214 爬楼全动态许可。R214 trace 中轮 dq/跳变本来可以高于当前门槛，所以此配置可能主动阻断高动态爬楼；首轮只允许低速平地、有界测试。

## 4. 你接下来要完成的开发顺序

### P0：静态代码审查（先做）

逐行审查：

1. `latest_remote_received` 的更新线程与读取线程是否有数据竞争；如有，用与现有共享状态一致的同步方式修复。
2. Warning→Brake、Hard→EmergencyDamping 与既有 A/B/Y/X、超时、编译门槛之间是否存在重复触发或状态覆盖。
3. 进入新状态时计数器、上一帧目标、命令斜率状态是否正确重置，避免旧 fault/旧 target 污染下一轮。
4. 守卫使用的是实际要发布的最终 `q/dq/kp/kd/tau`，而不是 raw action 或尚未 blend 的中间量。
5. 日志限频，不能在 500 Hz 发布环刷屏导致时序抖动。

修复后重新跑 x86 8/8 + `--offline-audit`，再同步 CPRO 三构建并记录新 SHA。不要在未发现问题时为了“重构漂亮”扩大改动面。

### P1：增加离线故障注入（无机器人动作）

优先扩展现有 `--offline-audit`，或添加独立的 guard audit，不要为了测试启动 DDS。至少验证：

1. safe envelope 连续多帧不触发；
2. warning 第 1–4 帧不触发，第 5 帧产生一次 Brake 请求；
3. hard 第 1–2 帧不触发，第 3 帧产生 EmergencyDamping 请求；
4. motorstate 非零走 hard 计数；
5. 200 ms remote invalid 产生 Brake；恢复合法帧不会自动重新进入 PolicyWalk；
6. 指令从 0 到各限幅端点，再回 0，逐帧斜率和总耗时符合配置；
7. `requested/applied` 与最终观测 command 一致，策略吃到的是整形后的命令。

如果现有函数紧耦合 FSM，先把纯计算与“请求状态切换”拆成可测小函数，不要复制另一套阈值。

### P2：文档与一键会话

更新 `一键现场会话与策略切换指南.md`：

- 启动时必须看到 `FIELD_SAFETY_PROFILE`；
- 解释 `WALK_CMD requested/applied`、`FIELD_SAFETY_WARN/HARD/SOFT_TRIP`、`REMOTE_TIMEOUT`；
- 明确 `Ctrl+C` 是操作员结束会话，发布端会清理并停发，但站立时停发仍可能下沉；优先 Y 受控趴下后再退出；
- 会话目录必须回收到本机 logs，不能只留 CPRO。

不要把阈值写成所有策略共享的永久常量。后续 B、L1+B 等不同策略应各自有策略合同与 safety profile；共用的是守卫机制。

### P3：有界真机验收（只有现场人员另行明确同意后）

第一轮不要直接开放自由 motion。建议顺序：

1. 只读基线：LowState 频率、mode_machine、原厂趴下、无已有 LowCmd 进程。
2. stand 回归：A→固定站立→Y受控趴下。守卫不应介入 FixStand/FixSquat；验证没有回归。
3. zero-B：A→B 强制零命令短接管→自动 Brake/回站→Y。检查无误触发和完整日志。
4. 若仍需 motion，单独做临时有界 launcher：只开放 `vx=±0.05 m/s`，`vy=wz=0`，非零最多 2 s，自动 Brake；不是自由摇杆会话。R214 平地持续运动已知存在后腿下沉，安全壳不能修复策略本身。
5. 每个步骤都是独立实验，重新说明动作/风险并重新获得许可。X/物理急停保留；Hard→EmergencyDamping 可能下沉。

不要因为编译/audit 通过就越过 one-key session 的 audit、LowState、控制权、16轴 mode0 和监测门槛。

### P4：现场日志判读

至少提取：

- 进入每个 FSM 状态的时间；
- `requested/applied` 三轴及达到限幅的时间；
- 16轴 q/dq/tau_est 峰值和对应时间/状态；
- 预计 PD 力矩与 tau_est 的差异；
- target step 峰值；
- warning/hard 连续计数和最终退出原因；
- motorstate/主板错误位；
- 操作员现场观感。

出现任何 guard 后，先解释“模型输出、包装、真实反馈还是阈值过窄”，不要直接放宽。阈值只可根据新的无异常真机证据逐策略调整。

## 5. HDC/CPRO 连接与构建事实

当前 WiFi HDC 目标为 `192.168.10.180:10178`。工作站工具：

`部署测试/00_HDC工具/hdc_6.1.1.280/hdc.exe`

使用规则：

- 先 `list targets -v`；目标丢失时再 `tconn 192.168.10.180:10178`。
- 命令显式加 `-t 192.168.10.180:10178`；不要 `hdc kill`、不要 `tmode`。
- `file send` 本机源必须是绝对路径。
- CPRO 机器人链 `eth0` 和 `ip rule` 不得修改。

本轮发现 `cpro_ubuntu.sh` 在全局 `/proc` 已挂载时会因重复 mount 报 `Resource busy`。临时构建使用了：

```bash
unshare --uts --fork chroot /data/ubuntu_in_hm/ubuntu_rootfs /bin/bash -lc '<build command>'
```

后续可单独把 helper 改成先检查 mountpoint 再挂载的幂等实现，但不要把这一非运动工具修复与安全壳源码混成一个大改动。
