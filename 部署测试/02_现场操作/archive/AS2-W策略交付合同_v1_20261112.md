# AS2-W 策略交付合同 v1

> **历史版本。** 训练方交付给部署方的现行清单为 `AS2-W训练到部署交付清单_v3_通用核心与按需模块.md`；后续新策略按通用核心与适用技能模块交付。本页保留 R1199 当时的审计背景。

适用范围：同事向本项目交付任何 AS2-W 轮足策略，包括新权重、重新导出的ONNX、动作包装更新、训练/评估脚本更新。交付物可先标为“离线研究版”，但只有下列**必填合同完整、可复现并通过对应门槛**才可进入CPRO候选构建；真机动作仍由现场人员逐次授权。R1199 的真实训练合同为连续/直行站姿补偿 `true/true`、停车里程计/关节稳态检查 `false/false`，而实机 C++ 走了另一套分支；此前还误拿较早权重的训练合同溯源。这说明必须把“权重+运行包装+正式评估开关”作为一个版本交付。

## 1. 每个版本的固定目录

```text
<policy-id>/
  README.md                 # 技能范围、已验证/未验证、是否建议实机
  manifest.yaml             # 唯一机器可读合同，见下文
  SHA256SUMS.txt             # 下列所有文件的哈希
  weights/                  # 原始checkpoint、导出ONNX、导出脚本
  runtime/                  # 完整观测构建、动作包装、状态更新与配置
  training/                 # 实际训练命令、配置、代码commit、环境版本与运行元数据
  assets/                   # 仿真模型/mesh/接触与执行器参数；可用明确哈希引用
  evaluation/               # 可重跑脚本、输入种子、逐例CSV/JSON、汇总和失败样例
  replay/                   # 固定输入→ONNX原始输出→最终16轴输出的逐帧夹具
```

允许体积大的权重/资产使用有权限的稳定下载地址，但 `manifest.yaml` 必须给出精确版本、SHA256、大小和获取方式；不能只给一个会随时间变化的 `main` 分支链接。交付时提供 Git commit 或不可变 tag、交付时间、联系人；`SHA256SUMS.txt` 与实际文件一致。训练服务器的绝对路径可作为溯源信息，不能成为唯一可读取方式。不要把密码、令牌、设备序列号放进包。

## 2. `manifest.yaml` 必填字段

以下是结构示意；每一项须填写实际数值或可定位文件，不能保留 `TODO`、`unknown` 或“见代码自行理解”。

```yaml
policy_id: as2w-rolling-<revision>
delivery_git_commit: <40位commit>
delivery_sha256: <zip哈希>
training:
  run_id: <不可变运行ID>
  source_commit: <训练代码commit>
  source_checkpoint: {path_or_uri: ..., sha256: ...}
  selected_checkpoint: {path_or_uri: ..., sha256: ...}
  exact_command_file: training/command.sh
  resolved_config_file: training/resolved_config.yaml
  actual_runtime_flags_file: training/runtime_flags.json
  command_distribution_file: training/command_distribution.json
model:
  onnx: {path: weights/policy.onnx, sha256: ..., opset: ..., ort_tested: ...}
  inputs: [{name: obs, shape: [1, 65], dtype: float32}]
  outputs: [{name: actions, shape: [1, 16], dtype: float32}]
  frequency_hz: 50
observation:
  index_table: runtime/observation_contract.csv
  normalization_file: runtime/normalization.yaml
  quaternion_and_gravity_frame: ...
  wheel_angle_wrap: ...
  velocity_source: ...
  previous_action: final_wrapped_action  # 或明确写raw_onnx_action
  history_reset_and_warmup: runtime/history.md
command:
  accepted_axes: [vx, wz]          # vy若不支持须明确声明
  frame_units_signs: runtime/command_contract.md
  training_ranges_and_probabilities: training/command_distribution.json
  filtering_deadzone_timeout: runtime/command_filter.yaml
action:
  joint_order: runtime/joints.csv   # 16个名字、腿/轮、正方向、单位
  raw_to_final_code: runtime/       # 包括所有后处理函数及其依赖
  exact_flags: runtime/flags.json   # 如continuous_bias/straight_bias/odometry/settle_joints
  target_and_gain_table: runtime/targets_gains.csv
  saturation_and_slew: runtime/limits.yaml
transition:
  supported_start_posture: runtime/entry_posture.yaml
  supported_stop_and_exit: runtime/exit.md
  maximum_target_step_evidence: evaluation/transition_steps.csv
simulation:
  assets_manifest: assets/manifest.json
  exact_commands: evaluation/run_commands.sh
  per_case_results: evaluation/results.csv
  summary: evaluation/summary.json
  initial_state_source: measured_lowstate_or_sim_proxy
release_status:
  simulation_gate: pass_or_fail
  hardware_candidate: true_or_false
  known_failures: README.md
```

`actual_runtime_flags_file`必须是**本次训练运行实际解析后的全部开关**，而非代码默认值清单或后来的正式评估配置。评估运行另给自己的 `evaluation/flags.json`；二者差异必须逐项列出、说明原因。不能让训练合同遗漏某开关、正式评估开关是true、诊断开关是false，而由部署人员猜哪个才是权威。每个策略可有不同的腿/轮 `kp/kd`；FixStand、策略、Brake、FixSquat 也分别给参数，不能把某版的55/2当跨策略常量。

## 3. 观测与动作的逐字段合同

- **观测**：每一维索引范围、名称、坐标系、单位、符号、缩放、裁剪、滤波、更新频率、缺测替代值、历史窗口、重置条件。机体系速度来自轮端估算还是仿真真值必须写清；实际机器人缺少的训练特权信息必须列明替代方案。四轮角度回绕、上一帧动作究竟是ONNX原始输出还是**最终包装后动作**，都须给固定回放例子。
- **命令**：`vx/vy/wz`哪些轴有用、哪个摇杆方向对应正/负、目标是物理机身速度还是轮速、训练分布（含零速概率、最低非零值、停走频率）、推理时死区/斜率/超时。不可把“支持转向”仅凭仿真视频概括；给定量范围与失败记录。
- **动作**：16轴关节名顺序、正方向、默认角、动作缩放与截断、轮速换算；ONNX原始输出后的每一项包装（例如 `rolling_fixed_exit`、停车、站立 `bias`、轮角参考）必须有完整源码与全部开关的实值。给出 `q/dq/kp/kd/tau` 的目标表，尤其动态切换是否连续；硬件DDS槽位由部署团队实测映射，不由训练方用其他机器人推断。

## 4. 必交的回放和仿真证据

1. **ONNX等价**：同一输入下 checkpoint→ONNX 原始16维动作误差；再做“观测→ONNX→动作包装→最终16轴目标→下一帧上一动作观测”的逐帧等价。至少一段零速、一段正负前后、一段小转向和一段反复停走；报告最大绝对误差、发生帧、输入与输出文件。仅对比原始ONNX不算完成。
2. **完整状态机路径**：从我们给出的实测FixStand `q/quat/dq` 启动，复现 `FixStand→PolicyHandoff→零速→+vx→松杆→−vx→松杆→Brake→ReturnStand→FixSquat`。至少包含停0.5/2/5秒、命令0.05和0.10 m/s；转向策略还需`±0.05 rad/s`。不同策略的入口站姿和增益须取其实际合同。记录目标角/实测角、轮目标/轮实测、躯干高度/俯仰、四轮载荷、非轮触地首次时间与峰值、每20ms目标跳步、最大关节速度/估算力矩、停车后额外位移。
3. **随机化与失败比例**：固定种子和独立种子、场景数量及分母、摩擦/执行器增益/延迟/推扰配置；单列无推扰和有推扰结果。失败例原始轨迹也要留，不接受只写“效果不错”“大部分成功”。Isaac、MuJoCo、部署环境的配置差异逐项列出。任何 `gate=false` 原样保留，不能将“安全门槛通过”写成“完整动作验收通过”。
4. **真实可用域**：如果仅前后可用就明确 `vy/wz` 未验收；如果松杆后仍滑动则给速度/位移分布；如果策略依赖额外支架、特定地面或低电量外条件，也在README首段写明。

## 5. 接收门槛和变更规则

- 交付包缺必填字段或哈希不符：标为**待补件**，可做只读研究，不能据此更新CPRO发布端或宣布可实机。确实不适用的字段用`not_applicable`并写原因，不能空缺。
- 包装或标志位有任何变化，即使ONNX权重SHA未变，也产生新的 `policy_id` 修订号、回放及仿真结果；不能用旧权重的旧评估报告替新包装背书。
- 部署团队按 `hardware_contract.md` 做机体映射、LowCmd和控制权门槛；训练交付方负责说明其关节/观测/动作/增益/运行开关。双方用同一固定输入逐帧比对最终目标，误差阈值按数据精度在交付包里明写。
- 对实机不确定项，README首页写“未验证”和具体风险。只有离线验收、ARM64编译/audit、只读影子、短时有界试验依次完成，并由现场人员对**每次具体动作**明确同意，才逐级开放长时摇杆。
